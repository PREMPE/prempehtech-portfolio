Secure IKEv2 Remote Access VPN

pfSense, Windows, Active Directory, Splunk, and least-privilege remote access.

I designed and implemented a secure remote-access VPN environment using pfSense Community Edition, IKEv2/IPsec, Windows, Active Directory, DNS, SMB file sharing, and Splunk Enterprise.

The goal was not simply to establish a working VPN tunnel. I wanted to control exactly what a remote user could access after connecting, while preventing unauthorized access to the rest of the internal environment.

View GitHub Repository Back to Projects

Project Overview

This project focused on building a realistic remote-access security model rather than a simple "connect and access everything" VPN.

I implemented network segmentation, split tunneling, least-privilege firewall rules, corporate DNS access, controlled SMB access, and centralized VPN authentication monitoring through Splunk.

I also performed both positive and negative testing to verify that authorized resources were reachable while unauthorized services remained blocked.

Project Objectives

Secure Remote Access

Establish an encrypted IKEv2/IPsec tunnel between a remote Windows endpoint and pfSense.

Network Segmentation

Keep remote VPN users isolated from internal server and client networks.

Least Privilege

Permit only specifically required corporate services.

Split Tunneling

Route only corporate networks through the VPN while allowing unrelated Internet traffic to use the client's normal connection.

Security Validation

Test both allowed and blocked connections to verify firewall policy enforcement.

Centralized Monitoring

Use Splunk to review VPN authentication activity.

Windows VPN Client

On the remote Windows system, I created an IKEv2 connection named: 

CORP Limited Guest VPN

The connection used IKEv2 tunneling, EAP authentication, and split tunneling.

I validated the VPN status using PowerShell: 

Get-VpnConnection -Name "CORP Limited Guest VPN"

After connecting, the remote system received an address from the dedicated VPN pool: 

VPN Pool:   172.16.60.0/24
VPN Client: 172.16.60.1

Split Tunneling

Instead of forcing all remote-client traffic through the VPN, I configured routes specifically for the internal corporate networks. 

172.16.10.0/24
172.16.20.0/24

Corporate traffic used the encrypted VPN tunnel, while unrelated Internet traffic continued using the remote client's normal Internet connection.

Least-Privilege Firewall Policy

Connecting to the VPN did not automatically give the user unrestricted access to the internal environment.

I created specific IPsec firewall rules to allow only the services required by the remote user. 

VPN USER
   |
   +-- DNS → DC01:53             ALLOW
   |
   +-- SMB → CLIENT01:445        ALLOW
   |
   +-- Other Corporate Access    BLOCK

Corporate DNS

Destination: 172.16.10.10

Port: TCP/UDP 53

SMB File Access

Destination: 172.16.20.101

Port: TCP 445

Default Deny

Other corporate traffic from the VPN network was blocked unless explicitly authorized.

Corporate DNS Validation

I tested internal name resolution directly against DC01: 

nslookup dc01.corp.local 172.16.10.10

The VPN client successfully resolved the internal domain controller, confirming that the explicitly permitted DNS traffic was reaching the corporate DNS service through the tunnel.

Controlled SMB File Access

I simulated a remote user who required access to a corporate file resource hosted on CLIENT01. 

\\172.16.20.101\GuestShare

I configured both pfSense and Windows Firewall policies so that the VPN network could reach CLIENT01 over TCP port 445.

Unauthorized Access Testing

I did not test only what the VPN user was allowed to access. I also validated that unauthorized services remained blocked.

From the VPN client, I tested access to SPLUNK01 on TCP port 9997: 

Test-NetConnection 172.16.10.30 -Port 9997

The connection failed as expected: 

TcpTestSucceeded : False

This demonstrated that the VPN tunnel could be fully operational while firewall rules still prevented unauthorized access to internal services.

Final Result

By the end of the project, the remote VPN user could successfully:

Encrypted VPN

Establish an IKEv2/IPsec tunnel.

EAP Authentication

Authenticate successfully through the VPN.

Isolated VPN Address

Receive an address from 172.16.60.0/24.

Corporate DNS

Query the internal DNS server.

Internal Resolution

Resolve internal corporate DNS records.

Authorized SMB

Access the approved GuestShare resource.

At the same time, the VPN user remained blocked from unrestricted access to corporate systems and from services that were not explicitly allowed by policy.

The project demonstrated that secure remote access is not only about allowing a user to establish a VPN connection. A complete design must also determine what the user can reach after connecting, what must remain blocked, and how authentication activity can be centrally monitored.
